# アーキテクチャ

Research Lab の仕組みを、要件・構成・データ・API・安全対策の順に説明します。操作の手順は [使い方.md](使い方.md) にあります。

## 何を解くためのアプリか

AI に研究を任せると、報告はもっともらしくても、元のデータや検証の結果をたどれなければ成果を信じられません。さらに運用では、別の担当が同じ仕事を始める、止めたはずの担当を起こし続ける、同じ改善提案が何度も届く、提案を採用しても効果が分からない、といった問題が起きます。

このアプリは、Vesuvius Challenge(炭化した古代の巻物を CT から読む懸賞金つきの課題)の研究で実際に使った管理 CLI から「仕組み」の部分を切り出し、特定の AI 製品に依存しないローカルアプリにしたものです。研究を進める **主担当**、根拠を確かめる **検証担当**、進め方を点検して提案する **監査役** の責務を、記録と状態で表します。授業での確認では、人が各役割を操作します。

AI モデルの実行や、巻物の画像処理そのものは含みません。成果が正しいかは、人が根拠を見て判断します。

## 要件 R1〜R6 との対応

元の研究体制で最初に合意した 6 つの要件を、このアプリの機能に対応させています。アプリ単体で元の目標を達成したと主張するものではありません。

| ID | 元の要件 | このアプリでの対応 | 範囲 |
|---|---|---|---|
| R1 | 成果を目指す。少ない支出で最初の受賞へ進む | 実験・判断・資源の記録と、採用した改善の結果を一覧にする | 進み具合を評価する材料を残す。受賞は保証しない |
| R2 | 大方針の範囲内で内側を自律的に進める | 主担当の登録、稼働状態、判断待ち、提案の採否、起こす判定 | 判断を 1 人の主担当に集める。自動研究は実装しない |
| R3 | 成果の信頼性を確かめられる | 根拠必須、フォルダ外の参照の拒否、SHA-256 の保存と照合、主張の確かさの分類 | 根拠と変更を追える。ハッシュだけで内容の正しさは証明できない |
| R4 | 費用・時間・計算資源・本人の対応負担を制御する | 資源・費用の記録、作業時間と本人の対応時間、一時停止・判断待ち、主担当の重複と同じ枠の起こしの拒否 | 投入の判断を助ける。課金の上限や外部ジョブの停止は強制しない |
| R5 | 研究するほど次が有利になる | 根拠を相対パスで持つ、実験・検証・判断の蓄積、未確認の点の記録 | プロジェクトのフォルダごと移して再利用できる |
| R6 | 研究の進め方自体を改善できる | 問題・変更・効果・負担・根拠を持つ監査提案、重複の防止、理由つきの採否、採用後の結果 | 提案から判断、効果の確認まで追える |

## 構成

```text
利用者(主担当・検証担当・監査役として操作)
        │  http://127.0.0.1:8780  (JSON)
        ▼
static/index.html   画面 1 枚(HTML・CSS・JavaScript を内包、外部 CDN なし)
        │  GET = 一覧と根拠の取得 / POST = 操作
        ▼
app.py              ThreadingHTTPServer。入口の検査、ルーティング、根拠の配信
        ├── tools/lab.py        中核:状態・記録・提案・受領・採否・結果・イベント
        └── tools/heartbeat.py  起こす判定:条件の検査と 30 分枠の予約
                │
                ▼
プロジェクトのフォルダ(--root / --demo / --research で選ぶ)
  ├── runtime/lab.sqlite3   SQLite の DB(記録とパス・ハッシュ)
  └── その他のファイル        根拠の実物(DB には複製しない)
```

周辺の道具:

| ファイル | 役割 |
|---|---|
| `seed_demo.py` | 巻物の平坦化を題材にした教材データを `projects/demo/` に作る |
| `tools/import_research.py` | 元の研究体制の DB から記録を全件写し、根拠を容量の範囲で選んで写す(提出物を作るときに 1 回だけ使った) |
| `smoke_check.py` | `app.py` を別プロセスで起動し、HTTP で主な操作をしてから止める |
| `tests/` | 中核・起こす判定・HTTP API・デモ・同梱した研究記録の自動テスト(36 本) |

### 依存を標準ライブラリだけにした理由

採点する PC には、元の研究体制にあった Codex・GPU・外部サービスがありません。`pip install` も要らない形にするため、`http.server`・`sqlite3`・`hashlib` だけで組みました。画面もビルド工程の無い HTML 1 枚です。元の体制にあった、特定製品の利用枠の読み取り、チャットの起動スクリプト、チャット ID が UUID であることの検査は持ち込んでいません。

## モジュール

### tools/lab.py(中核)

`Lab` クラスが 1 つのプロジェクトの DB を開き、全操作を持ちます。画面(app.py)と CLI の両方がこれを呼びます。

| メソッド | 中身 |
|---|---|
| `activate(thread_id, host_id)` | 主担当を登録して稼働中にする。稼働中に別の主担当なら拒否 |
| `pause()` / `hold(reason)` | 一時停止 / 理由つきの判断待ち |
| `record(data)` | 種類・確かさを検査し、根拠のハッシュを計算して保存 |
| `propose(data)` | 指紋を計算し、同じものがあれば既存を返す |
| `delivered(id, thread_id, host_id)` | 今の主担当と一致するか確かめて受領を記録 |
| `decide(id, decision, reason)` | 採否と理由を保存(理由必須) |
| `outcome(id, result)` | 採用した提案にだけ結果を書ける |
| `evidence(data)` | 根拠のパスを検査し、SHA-256 を計算する |

書き込みはすべて `BEGIN IMMEDIATE` のトランザクションで行い、画面と CLI から同時に操作しても順番に処理されます。

### tools/heartbeat.py(起こす判定)

`tick(lab, snapshot)` が、主担当の観測(名前・環境・観測時刻・待機中か・入力待ちか)を受け取り、次を順に確かめます。

1. 状態が `running`
2. 観測した主担当と環境が、今の登録と一致する(古い画面からの判定を弾く)
3. 観測から 60 秒以内で、未来の時刻でない
4. 待機中で、入力や承認を待っていない
5. 同じ主担当・環境・30 分枠で、まだ予約していない

全部満たせば `heartbeat_ticks` に予約を書き、`reserved` を返します。満たさなければ、満たさなかった条件を理由として返します。30 分枠は UTC の Unix 秒を 1800 で割った商です。予約は DB に残るので、再起動しても同じ枠では二度起こしません。

元の中核にあった送信アダプターの接続点は残しています。使う場合、送る直前にも待機中・判断待ちでないことを確かめる責務はアダプター側にあります。

### app.py(HTTP サーバー)

- 起動ごとに乱数の操作トークンを作り、画面の HTML に埋め込む
- `/api/evidence` と `/api/raw` で根拠を返す。返すのは「根拠の候補一覧」(`project_files`)に入っているファイルだけ
- 既定ポート 8780 が使えなければ、空いているポートに切り替える
- 要求の本文(研究ノート)はログに書かない

### static/index.html(画面)

`/api/state` で全体を 1 回取り、描き直します。状態の線、タブ、右の欄、根拠の縮小画像と照合のダイアログ、絞り込みを持ちます。画面は自動では更新せず、操作のあとと「最新に更新」で取り直します。

見た目は、状態の線と判断待ちの件数で「今どこで止まっていて、何が自分の判断待ちか」が先に目に入るようにしました。色は、操作が青緑、根拠の指紋が炭化した巻物にちなんだ焦げ茶、稼働中が緑、判断待ちが黄土、エラーが赤です。書体は日本語が読みやすい BIZ UDPゴシック(端末に無ければ代わりの書体)です。

## データモデル

DB はプロジェクトの中の `runtime/lab.sqlite3` です。時刻は UTC の ISO 形式で持ち、画面ではブラウザの現地時刻で出します。

| 表 | 主な列 | 用途と制約 |
|---|---|---|
| `control` | `id`, `phase`, `thread_id`, `host_id`, `waiting_reason` | `id=1` の 1 行だけ。今の状態・主担当・環境・判断待ちの理由 |
| `records` | `id`, `kind`, `created`, `payload` | 研究記録。`payload` は要約・根拠・確かさ・資源などの JSON |
| `proposals` | `id`, `created`, `fingerprint`, `payload`, `decision`, `reason`, `delivered_to`, `delivered_at`, `outcome` | 監査提案と受領・採否・理由・結果。`fingerprint` は UNIQUE |
| `events` | `id`, `created`, `action`, `payload` | すべての操作の履歴。採否を見直しても前の判断が残る |
| `heartbeat_ticks` | `thread`, `host`, `slot` | 起こす予約。3 列の複合主キーで同じ枠の重複を防ぐ |

根拠は `payload` の中に `[{"path": "evidence/result.txt", "sha256": "…"}]` の形で持ちます。ファイルそのものは DB に複製せず、プロジェクトのフォルダに置いたままにします。そのため、フォルダごと移せば別の PC でも照合できます。

`thread_id`(CLI では `--thread`)は元の体制との互換のために残した名前で、主担当の任意の名前を意味します。

### 状態の遷移

```text
prepared(準備中) ── 開始 ──> running(稼働中)
running ── 一時停止 ──> paused ── 開始 ──> running
running ── 理由つきで判断待ち ──> waiting ── 開始 ──> running
```

一時停止と判断待ちは、準備中からも入れます。稼働中のまま別の主担当・環境に切り替える操作は拒否します。

### 提案の重複判定と採否

同じ提案かどうかは、問題・変更・効果・負担・根拠のパスとハッシュを正規化した JSON の SHA-256(`fingerprint`)で決めます。完全に一致すれば既存の ID を返します。根拠の中身が変われば別の提案として登録できます。言い換えによる意味の重複までは見ません。

「受け取った」と「採否を決めた」は別の状態です。受け取っても、判断するまで受信箱に残ります。受領を記録するときは、稼働中であることと、主担当・環境の一致を確かめ直します。

## HTTP API

| メソッドとパス | 中身 |
|---|---|
| `GET /` | 画面(操作トークンを埋め込む) |
| `GET /api/state` | 状態・記録・提案・履歴・根拠の候補をまとめて返す |
| `GET /api/status`, `/api/files`, `/api/records`, `/api/inbox`, `/api/history`, `/api/events`, `/api/delivery` | 個別の一覧 |
| `GET /api/evidence?path=…` | 根拠の今のハッシュ、画像かどうか、テキストなら先頭 64 KiB |
| `GET /api/raw?path=…` | 画像の根拠をそのまま返す(PNG・JPEG・GIF・WebP だけ) |
| `POST /api/activate` | `thread_id`, `host_id` |
| `POST /api/pause` | `{}` |
| `POST /api/hold` | `reason` |
| `POST /api/record`, `/api/propose` | 記録・提案の JSON |
| `POST /api/decide` | `id`, `decision`(accept / defer / reject), `reason` |
| `POST /api/outcome` | `id`, `result` |
| `POST /api/delivered` | `id`, `thread_id`, `host_id` |
| `POST /api/heartbeat` | `thread_id`, `host_id`, `idle`(真偽値), `needs_input`(真偽値) |

入力の誤りは 400、操作元を確かめられないときは 403、無いパスは 404 を、どれも `{"error": "…"}` の JSON で返します。

根拠の候補に無いパスを指定したとき、ファイル自体が無ければ「この根拠ファイルは提出物に同梱していません…」、ファイルはあるが候補外(`runtime/` の DB など)なら「選択可能な根拠ファイルを指定してください」と返し分けます。

## 安全のための決まり

自分の PC で 1 人が使う前提で、次を守っています。

- **待ち受けは 127.0.0.1 だけ。** 同じネットワークの別の PC からは開けません。
- **Host の検査。** `Host` が `127.0.0.1:<ポート>` でない要求は 403(DNS リバインディング対策)。
- **POST は操作トークンが必須。** 起動ごとに作るトークンを `X-Lab-Token` に入れ、`Origin` も自分と一致するか確かめます。ほかのサイトのページから操作を送り込まれるのを防ぎます。
- **CSP。** スクリプトは起動ごとの nonce を付けたものだけ、読み込み先は自分だけ(`default-src 'self'`)、ほかのページへの埋め込みは禁止。
- **入力の上限。** 本文は 1 MiB まで、JSON の `NaN` などは拒否。
- **根拠はプロジェクトの中だけ。** `..` やリンクでフォルダの外を指すパスは拒否し、`runtime/`・`.` で始まるもの・`__pycache__` は候補にも出しません。DB を根拠として読み出すことはできません。
- **画面に出す文字はすべて `textContent` で入れる**(記録の中身を HTML として解釈しない)。

利用者ごとのログインや権限はありません。同じ PC の信頼できないプログラムからの防御や、公開サーバーとしての利用は対象外です。

## 同梱した研究記録(projects/vesuvius)

`tools/import_research.py` で、元の研究体制の DB から次を写しました。

| 項目 | 件数 |
|---|---|
| 研究記録 | 359 件(全件) |
| 監査提案 | 4 件(全件) |
| イベント | 22 件(全件) |
| 根拠ファイル | 2534 個のうち 1898 個、12.0 MB |

根拠は、1 ファイル 200 KB 以下のものを、研究の中身が分かりやすい順(Markdown → 画像 → JSON → テキスト → コード・パッチ → CSV → ログ)に、合計 12 MB まで入れました。CT の画像の束や大きなログまで入れると数 GB になるためです。入れなかった根拠も、記録・パス・ハッシュは残っており、画面では「同梱していない」と出ます。画像つきの記録は 19 件で、縮小画像は 28 枚です。

入れた根拠のうち 2 個は、元の研究で登録した後に書き換わっていたので、照合すると「変わっている」と出ます。取り込みでは中身に手を加えていません(`tests/test_research.py` で確かめています)。

記録の読み物としての要約は `研究成果/` にあります。

## 制限と今後

- 「一時停止」は管理上の状態で、外で動いている計算を止める機能ではありません。
- 起こす判定の「待機中」「入力待ち」は、利用者のチェックに頼っています。主担当の様子を自動で見る機能はありません。
- SHA-256 は登録後の変更を見つけるためのものです。根拠の真偽や、比べ方の正しさは保証しません。DB は直接書き換えられ、根拠の古い版も自動では残しません。
- 「別の担当が検証した」は利用者が選ぶ分類で、検証が済んだかを自動では判定しません。
- 根拠の候補一覧とハッシュの計算は、ファイルが多いと時間がかかります(同梱の 1898 個では体感できる差はありません)。
- 今後の候補:予算と実績の集計、根拠ファイルの版管理、検証担当の確認欄、提出用レポートの出力。
