# Vesuvius研究体制の基本設計

2026年11月11日に初期設計・実装。11月16日に既存の本人決定と稼働設定に合わせて記述を更新した。本人の指示により要件定義を完了し、[READMEの六要件](../README.md#合意した設計要件)を基本設計へ落とし込んだ。詳細設計書を別途増やさず、この基本設計とコードを対応させる。研究は本人から開始指示を受けた登録済み主担当チャットで進める。

初期構成は、研究全体と個別課題を兼ねる主担当、必要時の作業担当、成果の根拠を確認する検証担当、毎日定時に改善を提案する監査役とする。主担当はCodexのAstra / xhighの通常チャット。通常は主担当が次の研究を続け、復帰は主担当チャットへの直接heartbeatが担い、goalは完了条件のある個別課題の選択肢とする。実行中への差し込みの可能性は許容する。[heartbeatの実装状況](heartbeat.md)に制約と検証範囲を記載する。

本人の追加方針として、初期は研究を並列化しない。研究課題は一件ずつ進め、作業・検証を委任する場合も結果を受け取ってから次へ進む。日次監査は、この研究に外から改善を提案する役割として置く。

## 構成と接続

| 部品 | 実装 | 接続 |
|---|---|---|
| 主担当 | 通常のCodexチャット、`system/lead.md` | 稼働時のチャットIDを管理ツールへ登録。課題と提案の採否を判断 |
| 継続起動 | 既存主担当チャットへのCodex標準heartbeat | 現在3時間ごとの復帰機会。新しい起動担当チャットを作らない |
| 日次監査 | Codexの独立した定時実行、`system/auditor.md` | 毎日09:00 JST、Sol / high。提案を登録先の主担当へ送信 |
| 状態と提案の管理 | 標準Pythonの `tools/lab.py` | 主担当の登録、受信箱、配送状態、採否、改善結果をJSONで入出力 |
| 根拠 | 既存の `research/` と `experiments/` のファイル | 管理ツールがファイルの参照とSHA-256を索引に保存 |

管理データは `runtime/lab.sqlite3`。監査と主担当の更新がぶつかっても失われないようSQLiteのトランザクションを使う。研究の知識や元データをDBへ移す構成ではない。

監査はアプリの `send_message_to_thread` で登録先へ提案を届ける。送信に失敗した提案は未配送のまま残り、主担当が受信箱からも読める。正常な配送と主担当の採否は別の状態として扱う。

実装範囲は主担当への指示、監査の定時登録、記録・提案の受け渡し。実験実行は主担当が既存ツールを使う。lab自体は有料台の調達や強制的な課金上限を提供しない。Runpodは11月14日の本人委任の範囲内で主担当が実験ごとに判断し、他の有料計算は本人の承認と既存計算基盤で扱う。

## 責務と判断の所在

| 担当 | 責務 | 判断できる範囲 |
|---|---|---|
| 本人 | 活動の分野、大方針、大きな投資判断 | Vesuviusへの挑戦、活動全体の継続・転換、支出の委任範囲 |
| 主担当 | 研究候補の比較、課題の選択、研究、担当配分、成果の採用、体制改善 | 合意した方針の内側で仮説や方法を変更し、個別課題を継続・切替・打ち切りできる |
| 必要時の作業担当 | 分離して進められる調査・実装・実験 | 主担当から渡された目的と資源範囲内で方法を選ぶ |
| 必要時の検証担当 | 成果の主張を、実物の証拠で確認する | 根拠の不足、反例、比較の不成立を示し、確認できた範囲を報告する |
| 日次の監査役 | 外から研究の進め方と投入を見て、ボトルネックや改善機会を主担当へ提案する | 証拠を調べて改善を提案する。採用・実施の判断は主担当にある |

担当は常設の人数ではなく責務を表す。主担当が直接作業する場合もある。委任は、切り分けられる作業、別の仮説の検討、成果の検証などに必要時に使い、初期は逐次進める。主担当が依頼と結果の取り込みを担い、本人が各担当を管理する構成にはしない。

主担当の任務は初受賞に向けて研究と成果化を進めること。特定の仮説を解けるまで追い続けることには固定しない。成果化には、応募先が評価できる説明・比較・成果物を整えることも含む。提出や公開の実行権限は、今回の設計開始の指示から拡張しない。

## 投入先を変える判断

課題を選ぶ際には、報酬につながる道筋、次の小さい試行で分かること、必要資源、残せる知識や道具を比較する。確率の根拠がない段階で、受賞期待値を数値化して順位を決めない。

個別の研究には、次に判定したい問いと、投入の目安・見直す時点を主担当が置く。重要な結果が出た、見込みが下がった、予定した投入に達した場合に、続行・切替・打ち切りを判断する。これらを細かな承認事項として本人へ戻さない。

11月13日の本人決定により発見を研究の主目標とし、その過程の改善を既存三件とともに蓄積する。11月16日の外部監査について、本人は受賞への前進・知識と道具の蓄積・進め方の改善を等価に評価すると決めた。再利用のための整備には、具体的な次の用途や繰り返し生じた負担との関係を持たせる。投入配分は個別票だけでなく一連の研究の成果と未解決点から見直す。[現在の配分判断](research-allocation-20261116.md)。

## 信頼性を支える検証

探索中の試行は、担当が内容に応じて確かめる。提出・追加投資・再利用の根拠になる重要な成果の主張には、作った担当とは別の確認を使う。別担当は説明の読み直しだけでなく、入力データ、コード、実行条件、生の結果、比較対象にアクセスして、主張が崩れる可能性を調べる。

再実行で一致することと、評価方法が正しいことは別に扱う。同じ誤った比較を再現しただけでは改善の根拠にならない。比較条件の差、評価データの混入、対象範囲の偏りなど、主張に関係する点を確認する。検証方法と深さは成果ごとに選び、全作業を一律に二重化しない。

意見が割れた場合は、判定を変えられる追加確認を選ぶ。根拠が足りなければ主張を暫定に留める。主担当は技術的な食い違いの解決を本人へ預けず、資源範囲内で追加確認するか、その成果への依存を下げる。

例えば、画像処理のメモリ削減を成果とするなら、元の処理との条件を揃え、出力の同等性、メモリ使用量、処理時間を比較する。検証済みの改善と、賞の対象として評価されるかは区別する。これは設計の説明例であり、次に着手する課題の決定ではない。

## 資源の配分と終了

主担当が、作業担当・計算・検証・再試行・日次監査を含めた投入をまとめて把握する。個々の仕事が小さくても、合計の支出と時間を見て配分する。

有料実験は、何を判断する実験か、見積額とその前提、運用上の支出上限、終了条件を提示する。Runpodの必要分は11月14日の本人決定により主担当が判断でき、各回の支出再承認は不要。他サービスは実験ごとの承認が必要。研究体制の自己改善によって、この権限を広げることはできない。運用上限は事業者の強制上限ではない。

計算を終了・打ち切りにした際は、主担当が委任先や計算ジョブの停止、残る保管費用まで確認する。有料実験の計画時には、使用する計算基盤での停止方法と支出確認方法も具体化する。見積もりと実績がずれた場合は、次の配分に反映する。

モデルとeffortは委任ごとに選ぶ。未確定の研究設計や難しい判断にはAstraと高いeffort、手順のある実装や資料整理にはSolなど作業に適したモデルを候補にする。初期の割当は仮説として扱い、成果の質、所要時間、使用量から変更する。モデル名や別担当であること自体を正しさの根拠にしない。

## 知識と道具の蓄積

蓄積の単位は、次の研究に利用できる知見と、その根拠・適用範囲。再現に必要な入力や版、コード、実行条件、結果と費用を成果物に結びつける。失敗も、どの条件で何が成立しなかったかが次の判断を変えるなら残す。

置き場は既存のプロジェクト内の文書・コード・実験結果を利用する。道具の共通化は、再利用する具体的な場面に合わせて進める。記録は信頼性と再利用のために置き、削除されたセッション間継続の要件を復活させる目的では設計しない。

## 体制そのものの変更

主担当は研究上の停滞と、進め方による停滞を分けて考える。証拠が出るまでの時間、検証での手戻り、重複作業、調整待ち、本人への対応依頼などに負担が現れたら、その原因に対応する変更を試す。変更後に負担や成果がどう変わったかを見て、維持・修正・撤回を決める。

### 日次監査による改善提案

本人案は、監査役を毎日定時に起動し、主担当とは別の視点から改善を提案させるもの。監査役を初期構成に加え、日々の研究に埋もれやすい投入配分や進め方を見直す機会を持たせる。

監査役は、主担当の説明だけでなく、既存の実験結果・変更内容・実行や費用の記録を参照する。主担当に監査用の報告書を毎回作らせる構成にはしない。見る対象は、個別成果の正しさに加えて、研究の選び方、投入と得られたものの釣り合い、繰り返す手戻り、活用できていない知識や道具など。各項目を全件点検する固定手順にはせず、その日に提案価値がある点を選ぶ。

提案は、観察した事実、変える案、期待する効果と必要な負担が分かる短い形で主担当へ渡す。材料が足りない点は推測として区別する。有意な提案がない日は通知を増やさず、同じ提案の再送は状況や根拠が変わった場合に絞る。

主担当は次の研究判断で提案を扱い、採用・保留・不採用を自律的に決める。監査役から本人への定例の承認依頼は作らない。採否と簡単な理由、採用後の結果は次の監査でも参照できるようにし、提案が役立ったかを見直す。監査役自身による実験・計算の起動や構成の変更は、この役割には含めない。

監査には実行時間とトークン、主担当には提案を読む負担が生じる。「負荷がほぼない」は初期の見込みとして扱い、監査と提案処理の負担を、実際の改善と比較する。監査の範囲と投入量は主担当が調整する。日次監査の頻度変更は、その結果を踏まえて検討する。

監査役による観察は、実行側の資源制御や、成果を採用する際の検証と併用する。毎日09:00 JSTに起動する定時実行をPAUSEDで登録し、研究開始後に有効化する。初期の監査はSol / highで既存記録の点検に限定し、その実行負担も改善対象に含める。

| 実際に観察された問題 | 検討する構成変更 |
|---|---|
| 将来、研究の並列化を採用した後に、研究間の配分・競合調整が負担になる | 全体の配分を担う管理役と、個別研究の主担当を分ける |
| 同じ種類の確認漏れや検証の待ちが繰り返される | 検証担当の分担や、該当する検査の自動化を見直す |
| 同じ処理の再実装・準備が繰り返し負担になる | その部分を再利用できる道具にする |

いずれも自動的な導入条件ではなく、構成変更を検討する根拠。初期段階では主担当に変更判断を集め、常設の上位管理役は置かない。研究の並列化は将来の検討事項であり、本人が示した当面の逐次実行の方針を体制改善だけで変更しない。本人が決めた方針や投資範囲を変える場合は、本人の判断に戻す。

## 六要件への対応

| 要件 | 対応する設計 |
|---|---|
| R1 成果 | 主担当が報酬への道筋と次に得る証拠を比較し、成果化まで扱う |
| R2 自律 | 方針内の課題選択・研究・配分・停止を主担当が決める |
| R3 信頼性 | 重要な主張に対する別担当の実物検証と、根拠の保存 |
| R4 資源 | 委任・再試行・日次監査を含む投入管理、支出の委任範囲、終了時の停止確認 |
| R5 蓄積 | 知見の適用範囲と根拠、再利用できるコード・評価方法 |
| R6 改善 | 日次監査で外から改善を提案し、主担当が採否と実施を判断する。変更の効果を見て構成を調整する |

操作方法と動作確認の範囲は [運用手順](operations.md)。固定の研究工程、常設の多階層組織、セッション引継ぎ基盤は初期構成に含めない。
