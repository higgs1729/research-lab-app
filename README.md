## 1. アプリ概要・コンセプト

* **どんなアプリか（一言で）**：  
  AI に研究を自律的に進めさせるときに、研究の状態・根拠ファイルつきの記録・監査役からの改善提案とその採否を一つの画面で管理する、ブラウザで使う研究管理アプリです。
* **ターゲットユーザー・利用シーン**：  
  AI エージェントに長い研究や開発を任せたい個人。実際に、懸賞金のかかった未解決問題(Vesuvius Challenge:炭化した古代の巻物を CT から読む)を AI に研究させる体制の中核として使ったものを、誰の PC でも動く形に切り出しました。
* **一番のこだわり・アピールポイント**：  
  AI の「もっともらしい報告」を信じ込まないための仕組みです。研究記録は根拠ファイルが無いと登録できず、登録時にファイルの SHA-256 を保存して、後で中身が変わっていないかを画面で照合できます。監査役の提案は同じものを二重に登録できず、採否には理由を必須にし、採用後の結果まで追えます。主担当が二人同時に動くことや、作業中の主担当を何度も起こすことも、仕組みの側で防ぎます。要件(R1〜R6)を先に決め、基本設計をしてから実装しました(詳しくは `docs/アーキテクチャ.md`)。  
  画面は、最初に AI が作ったものが「いかにも AI が作った」見た目だったので作り直しました。上部に「準備中 ― 稼働中 ― 一時停止 ― 判断待ち」の線を置いて今の状態を点灯させ、判断を待っている提案の数をタブに目立たせて、「今どこで止まっていて、何が自分の判断待ちか」が一目で分かるようにしています。根拠ファイルの指紋(ハッシュの先頭)は、炭化した巻物にちなんだ焦げ茶で表示しています。

## 2. 実装した機能一覧

- [x] 研究の状態管理(準備中/稼働中/一時停止/判断待ち)と主担当の登録。稼働中に別の主担当へ切り替える操作は拒否
- [x] 根拠ファイルつきの研究記録(実験・検証・判断・費用・監査)。根拠なし・フォルダ外のファイルは拒否し、SHA-256 を保存
- [x] 根拠の照合:登録時のハッシュと今のファイルを比べ、変わっていれば赤で表示
- [x] 監査提案の受信箱:二重登録の防止、採用/保留/不採用(理由必須)、採用後の結果の記入、採否の履歴
- [x] ハートビート判定:主担当が待機中のときだけ、30 分枠ごとに 1 回だけ起こしの予約をする
- [x] イベント履歴(すべての操作を時系列で表示)とエラー表示
- [x] 拡張機能:同じ中核をコマンドライン(CLI)と JSON の HTTP API からも使える
- [x] 拡張機能:巻物の平坦化を題材にしたデモデータの自動生成(`--demo`)
- [x] 拡張機能:自動テスト 36 本(中核・ハートビート・HTTP API・デモ・同梱した研究記録)
- [x] 拡張機能:実際の研究記録 359 件を同梱し、そのまま画面で開ける(`--research`)
- [x] 拡張機能:画像の根拠を縮小表示し、押すと拡大して照合できる
- [x] 拡張機能:研究記録の絞り込み(文字・種類・画像つきだけ)
- [x] 拡張機能:研究成果の読み物(`研究成果/`)と、説明書・アーキテクチャの文書(`docs/`)

## 3. 開発環境・起動手順

### 使用技術スタック
* **使用言語**：Python 3.11 以上 / HTML / CSS / JavaScript
* **フレームワーク・ライブラリ**：なし(Python の標準ライブラリのみ。`http.server`・`sqlite3`・`hashlib` を使用。外部 CDN も不使用)

### アプリの起動方法
1. **事前準備・インストール（必要な場合のみ記載）**
   ```bash
   # インストールは不要です。Python 3.11 以上が入っていることだけ確認してください
   python --version
   ```
2. **実行手順・コマンド**
   ```bash
   # このフォルダ(app.py がある場所)でターミナルを開いて実行
   python app.py --demo

   # 既定のブラウザで http://127.0.0.1:8780 が開き、デモデータの入った画面が出ます

   # 実際の研究で使った記録(359 件)を開く場合
   python app.py --research
   # 8780 番が使用中なら自動で空いているポートに切り替わります(ターミナルに表示された URL を開いてください)
   # 終了はターミナルで Ctrl+C

   # 自動テスト
   python -m unittest
   ```

役割分担:元の研究体制では、Codex のチャットを「主担当」(研究を進める)と「日次監査役」(進め方を点検して提案する)にし、このアプリの中核(`tools/lab.py`)でつないでいました。提出用への切り出しでは、Claude Code が既存のコードを読んで設計と依頼文を書き、実装を Codex に任せ、Claude Code が動作確認と修正をしました。

### 4-2. 思い通りのコードを引き出すための「プロンプトの工夫」

> **【実際にAIに送ったプロンプト（コピペ）】**  
> (Claude Code から Codex へ送った依頼文の一部)  
> 「`C:/dev/kensyoukin` は、AI エージェントに研究を自律的に進めさせるための体制。その『仕組み』部分を切り出し、学校の個人課題として提出できる形にする。採点者は別の PC で動かす前提。Codex アプリや外部サービス、GPU は無い。(中略)**C:/dev/kensyoukin は一切書き換えない**。(中略)挙動と検証(根拠必須、二重提案の防止、稼働中の別主担当の拒否、配送先の一致確認など)は落とさない。軽い GUI:Python 標準ライブラリだけ(`http.server` + 1 枚の HTML/CSS/JS、外部 CDN なし)。(中略)確かめ方:`python -m unittest` が全部通る。起動して HTTP で主要エンドポイントを叩いて期待どおり返ることを確かめてから止める。」

* **工夫したポイント・なぜこの指示が有効だったか**：  
  1. **「誰がどこで動かすか」を最初に書いた。** 「採点者の PC には Codex も GPU も無い」と書いたことで、AI が特定の製品に依存する部分(利用枠の読み取り、チャットの ID が UUID でないと通らない検査など)を自分で見つけて外し、標準ライブラリだけで動く形を選びました。
  2. **「書いてよい範囲」と「書き換えてはいけない範囲」を分けた。** 元の研究体制は今も動いているので、元フォルダは読むだけと明記しました。
  3. **「落としてはいけない性質」を列挙した。** 「GUI を付けて」とだけ頼むと、見た目に気を取られて検証の仕組みが簡略化されがちです。根拠必須・二重登録防止などを名指しで残させました。
  4. **完了の確かめ方を指定した。** 「テストが全部通る」「実際に起動して叩いてから止める」と書いたので、AI がテスト 33 本と HTTP の動作確認まで自分で回してから報告しました。

  元の研究体制を作るときも、いきなり作らせずに「要件定義 → 基本設計 → 実装」の順で AI と進めました。要件は「成果を目指す」「内側を自律的に進める」「成果の信頼性を確かめられる」「資源を制御できる」「研究するほど次が有利になる」「進め方自体を改善できる」の 6 つ(R1〜R6)で、AI の案から「セッションを越えて継続できる」などの不要な要件を削ってから合意しました。

### 4-3. エラー・バグ解決の記録（デバッグの足跡）

* **発生したトラブル・エラー内容**：  
  AI が作ったアプリを `python app.py --demo` で起動すると、`起動できません: [WinError 10013] アクセス許可で禁じられた方法でソケットにアクセスしようとしました。` で止まった。AI 側のテストは全部通っていた。
* **AIへの聞き方と解決プロセス**：  
  エラー文をそのまま Claude Code に渡して調べさせました。AI はエラー番号から「ポートが使えない」と見当をつけ、`Get-NetTCPConnection -LocalPort 8765` で既定ポートの 8765 番を自分の PC の別のツールがすでに使っていることを突き止めました。テストは空いているポートを自動で選ぶ設定で動いていたため、この問題に気づけなかったのです。採点する PC でも同じことが起こりうるので、既定ポートを 8780 に変え、さらに「指定したポートが使えなければ空いているポートへ自動で切り替える」処理を `app.py` に追加して解決しました。

  元の研究体制でも、AI の作業が止まる不具合がありました。Codex の週の利用枠が 99% に達した直後、主担当が応答のないまま止まり、再開を伝えるまで 3.1 時間と 12.8 時間止まりました。止まっている間は起こしの仕組み(ハートビート)も届かないと分かったため、残量を読むツールを作り、「尽きる見込みが立った時点で引き継ぎを残して知らせる」という手順を主担当の役割に足しました。

## 5. 開発を通じた振り返り・学び

AI は、決まった仕様をコードにする速さと、テストを網羅的に書く力が圧倒的でした。一方で、次のことは人間が決めないといけないと感じました。

* **何を作るか、何を作らないか。** AI に要件を出させると増える方向に寄るので、本当に必要なものを選んで削るのは自分の仕事でした。
* **AI の報告をそのまま信じないこと。** 研究では、AI が「改善した」と報告しても、別の指標では悪化していることがよくありました(研究成果の R005 の記録に多く残っています)。だから「根拠ファイル必須」「作った担当と別の担当が検証する」を仕組みにしました。今回の開発でも「テストは全部通った」のに、自分の PC では起動しませんでした。テストが確かめている範囲と実際の使われ方のずれは、実際に動かして初めて分かります。
* **依頼文の質が結果を決める。** 前提(動かす環境)・範囲(触ってよい場所)・守る性質・完了の確かめ方の 4 つを書くと、一回で使えるものが返ってきました。

次回は、予算と実績の集計や、根拠ファイルの版管理を加えて、研究体制をそのままこのアプリで回せるようにしたいです。

* `projects/vesuvius/`:実際の研究記録(DB と根拠ファイル)。`--research` で開く / `projects/demo/`:`--demo` で作る教材データ(初回に作り、以後は操作した状態を残す)
* `tools/import_research.py`:元の研究体制から記録を写した道具(提出物を作るときに 1 回だけ使用)

**根拠ファイルは一部だけ同梱しています。** 研究記録は 359 件すべて入っていますが、根拠ファイルは 2534 個のうち 1898 個(12.0 MB)だけです。CT の画像の束や大きなログまで入れると数 GB になるため、1 ファイル 200 KB 以下のものを優先度順に選びました。入れなかった根拠も記録とハッシュは残っていて、画面では「同梱していない」と表示されます。画像(PNG・JPEG など)の根拠は入れてあり、画面で見られます(画像つきの記録 19 件、28 枚)。
